# 作成の経緯

このアプリを、どういう順番で考え、どう作り、どこで判断したかの記録です。全データは架空です。

## 進め方の全体像
```mermaid
flowchart LR
  A[業務の洗い出し] --> B[課題と置き換えの対応表]
  B --> C[仕様書]
  C --> D[仕様書の独立レビュー]
  D --> C
  D --> E[AIエージェントによる実装]
  E --> F[AIによるコードレビュー・最終検査]
  F --> E
  F --> G[人の受け入れ判断]
  G --> H[公開用に整理]
```

| 段階 | やったこと | 成果物 |
|---|---|---|
| 1. 業務の洗い出し | 外国人スタッフを雇う会社の総務担当者が、今どう在留期限と書類を管理しているかを「誰が・何を・どうする」の手順に分けた（Excel台帳、月1回の目視確認、拠点ごとの台帳共有など。架空の会社を想定） | 業務手順の一覧 |
| 2. 課題と置き換え | 手順ごとに「何が起きているか」と「どの機能で置き換えるか」を対応させた | [仕様書](specification.md) の2章 |
| 3. 仕様を決める | 利用者と権限 → 画面 → テーブル → 裏で動く処理 → 出力 → テスト方針の順に決めた。「やらないこと」も先に書いた | [仕様書](specification.md)、[ER図](er.md) |
| 4. 仕様書のレビュー | 書いた本人とは別のAIに仕様書を読ませ、抜け・矛盾を指摘させて直した（3版まで） | 仕様書の改訂 |
| 5. 実装 | 役割を分けたAIエージェント（実装役・レビュー役・最終確認役）に、仕様書とコーディング規約を渡して実装させた | アプリ本体、テスト285件 |
| 6. 検証 | テスト全件合格・RuboCop違反0・カバレッジを実測し、起動バッチで実際に起動して確認した | [テスト仕様と結果](testing.md) |
| 7. 受け入れ | レビューの指摘と検証結果を見て、受け入れるかを人が判断した | [レビュー・設計判断の記録](review_log.md) |

## 人とAIの役割分担
- **人が決めたこと**：題材、解決する課題、権限の考え方、「やらないこと」、受け入れの判断。
- **AIに任せたこと**：仕様書に沿ったコードとテストを書くこと、コードレビュー、テストの実行。
- **AIに任せるための工夫**：
  - 取り違えると困る決まり（テナントの取り方、区分の判定、日付の扱い）は [コーディング規約](coding_guidelines.md) に1か所で書き、毎回同じ文で渡した。
  - 規約を守っているかを人の目だけに頼らず、テスト（`spec/lint/`）で機械的に検出するようにした。
  - 「テストを削って通す」ことを禁止し、落ちたら原因を直させた。

## 途中で判断したこと
| 場面 | 判断 | 理由 |
|---|---|---|
| データの分け方 | 子テーブルにも `organization_id` を直接持たせ、親子の一致をモデルで検証 | 親をたどる結合に頼るより、取り違えが起きにくく、検索も単純になる |
| 在留カード | 上書きせず履歴として追加し、カード番号は下4桁のみ | 更新の経緯を残す。番号全体は持たない方が漏えい時の被害が小さい |
| スタッフの削除 | 削除せず「退職」状態にする | 監査ログや書類の履歴が宙に浮かないように |
| 他組織のID | 403ではなく404 | 「そのデータが存在する」こと自体を他社に知らせない |
| 定期実行 | 常駐のジョブ基盤を使わず、起動時・画面のボタン・コマンドで代替 | Windows では標準のジョブ基盤が動かない。デモの手軽さを優先 |
| 通知の二重作成 | 「カード×区分」に一意制約を付けて冪等に | 何度動かしても安全にするため、アプリの判定だけでなくDBでも守る |
| AIのお知らせ文下書き | 今回は範囲から外した | 期限内に、テストで品質を確かめられる範囲を優先した |
| 権限の仕組み | 外部gemを使わず小さな Policy クラスで自作 | 規模が小さく、読む人が仕組みをすぐ追える方を優先 |

## 実装中に起きたこと
- **日本語を含むフォルダで起動できない**：Windows の Ruby で、日本語を含むパスにあると `bin/rails` がパスを読み違えて止まった。英数字のパスに置く前提にし、起動手順とREADMEに明記した。
- **エラーメッセージが画面に出ない不具合**：書類の不正な状態変更で422を返しても、エラーが画面に出ていなかった。レビューで見つけて直し、テストで固定した。
- **テスト自体の不備**：「必須項目が空」のテストが、実は空にできておらず空振りしていた。テスト側を直して、本当に検査しているかを確かめた。
- 詳しくは [レビュー・設計判断の記録](review_log.md)。
